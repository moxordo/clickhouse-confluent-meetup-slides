Slide 08 / 17Pipeline
DARO 데이터 파이프라인
실시간 이벤트 경로: App SDK → DARO API → Confluent Kafka → S3 → S3Queue Engine → ClickHouse
정산 배치 경로: DARO Report Fetcher (SSP API 폴링) → S3 → Airflow → REPLACE PARTITION
S3가 허브 역할 — 실시간 스트림과 배치 정산 데이터가 모두 S3를 통해 ClickHouse로 들어옵니다.
다이어그램의 세 레인: 이벤트 스트림 / S3Queue 자동 적재 / 정산 배치

Slide 09 / 17Freshness
신선도: S3Queue Engine
기존 방식: Airflow DAG가 S3를 폴링해서 ClickHouse에 INSERT — 운영 복잡도 높음, 지연 존재
S3Queue Engine: ClickHouse가 S3를 직접 watch하여 새 파일이 생기는 즉시 자동 적재. Airflow DAG 불필요.
설정은 CREATE TABLE ... ENGINE = S3Queue(...) DDL 하나로 끝 — 별도 오케스트레이션 없음
비교 표에서 Latency / Ops overhead / 설정 복잡도 세 항목 모두 S3Queue 우위임을 강조하세요.

Slide 10 / 17Accuracy
정확도: REPLACE PARTITION
ALTER TABLE t REPLACE PARTITION p FROM t_tmp — 파티션 전체를 원자적으로(Atomically) 교체합니다.
D+7 확정 데이터가 도착하면 해당 날짜 파티션만 통째로 swap → 쿼리 중단 없이 정확도 확보
DELETE + INSERT 방식 대비: 중간 상태 없음 / 롤백 가능 / 쿼리 일관성 보장
공식 문서 스크린샷 슬라이드 — 간략히 설명하고 넘어가도 됩니다.

Slide 11 / 17Key Slide
하나의 테이블로 신선도와 정확도 동시에
agg_ssp_impression (AggregatingMergeTree) — 실시간 집계 상태(-State)와 확정치를 같은 테이블에 공존시킵니다.
실시간 경로: stg_ssp__impression(S3Queue) → Materialized View → agg_ssp_impression 자동 누적
배치 경로: finalized_s3_source → REPLACE PARTITION (daily) → 확정 파티션 교체
쿼리 시 sumMerge / uniqMerge로 -State를 최종화 — 이것이 AggregatingMergeTree의 핵심 패턴입니다.
이 슬라이드가 오늘 발표의 핵심 — 시간이 부족하면 여기에 집중하세요.

Slide 15 / 17Takeaway 01
준실시간 스트림 집계 + 백필 집계를 하나의 테이블에
복잡한 파이프라인 없이 ClickHouse DDL + DML만으로 설정 가능합니다.
Materialized View가 실시간으로 -State 집계를 누적하고,
REPLACE PARTITION이 확정 데이터로 해당 파티션을 원자적으로 교체합니다.
쿼리 시 sumMerge / uniqMerge로 집계 상태를 최종화.
15 / 17
Slide 16 / 17Takeaway 02
REPLACE PARTITION으로 재처리 파이프라인이 단순해집니다
4-step 워크플로우: CREATE TABLE tmp AS src → INSERT INTO tmp → REPLACE PARTITION → DROP TABLE tmp
Airflow DAG는 create_tmp >> load_tmp >> replace 세 태스크로 끝 — 멱등성(Idempotent) 보장
재실행해도 안전: tmp 테이블을 매번 새로 만들고 지우기 때문에 중복 데이터 걱정 없음
DELETE + UPSERT 방식 대비: 중간에 쿼리해도 항상 일관된 결과 / 파티션 단위 원자성

Slide 17 / 17Closing
감사합니다 — Q&A
질문이 있으시면 편하게 말씀해 주세요.
예상 질문 1 — AggregatingMergeTree에서 -State와 -Merge 함수를 꼭 써야 하나요? → 네, AggMT는 raw 값이 아닌 직렬화된 집계 상태를 저장하기 때문에 반드시 쌍으로 써야 합니다.
예상 질문 2 — REPLACE PARTITION 중 쿼리가 날아오면? → ClickHouse는 파티션 레벨 atomic swap이라 쿼리 결과가 old 또는 new 파티션을 완전히 읽습니다. 중간 상태 없음.
예상 질문 3 — S3Queue Engine은 exactly-once인가요? → at-least-once입니다. S3Queue 자체는 중복 가능 — AggregatingMergeTree의 집계 특성으로 멱등성을 확보하는 구조입니다.
