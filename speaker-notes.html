01 / 17Title
ClickHouse를 활용한 광고 데이터의 신선도와 정확도
오늘은 저희 DARO 광고 수익 파이프라인을 ClickHouse로 어떻게 구현했는지 실전 사례를 공유해드리려 합니다. 기술 스택은 심플합니다. Confluent Kafka → S3 → ClickHouse Cloud. 그런데 이 심플한 스택으로 두 가지 상충되는 요구사항을 동시에 만족시켜야 했습니다. 신선도 — 광고 수익을 준실시간으로 보여주는 것, 그리고 정확도 — D+7 기준 확정 수치로 정기적으로 보정하는 것. 이 두 가지를 하나의 테이블로 어떻게 풀었는지가 오늘 발표의 핵심입니다. 끝에 Q&A 시간을 드리겠습니다. 편하게 질문해주세요.

DelightRoom 소개

05 / 17DARO
DARO에서의 챌린지
DARO는 약 5,000만 MAU에 200개 이상의 파트너사 광고 수익을 집계해서 대시보드로 보여주는 플랫폼입니다. 파트너사(퍼블리셔) 입장에서는 두 가지가 필요합니다. 첫째, 지금 제 광고가 얼마나 벌고 있는지 빠르게 보고 싶다. 둘째, 월말 정산 때 정확한 수치가 맞아야 한다. 이 두 가지가 기술적으로 충돌합니다. 실시간 수치는 항상 preliminary이고, SSP에서 D+7 기준으로 확정 수치가 뒤늦게 들어오기 때문입니다. "빠르게도, 정확하게도" — 이게 오늘 풀어드릴 문제입니다.

06 / 17Requirements
신선도 + 정확도의 요구사항
신선도(Freshness) 측면에서는 두 가지가 중요합니다. 새 퍼블리셔가 온보딩됐을 때 즉시 수익 데이터가 보여야 하고, A/B 실험 중에는 준실시간 성과 피드백이 필요합니다. 정확도(Accuracy) 측면에서는, SSP 집계가 지연되고 보정되기 때문에 처음 받은 수치는 항상 preliminary입니다. D+7 기준으로 확정 수치가 들어오면 해당 기간 데이터를 정확하게 업데이트해야 합니다. 두 요구사항이 충돌하는 것처럼 보이죠. 다음 슬라이드들에서 ClickHouse로 어떻게 동시에 만족시켰는지 보여드립니다.

08 / 17Pipeline
DARO 데이터 파이프라인
파이프라인은 크게 두 경로입니다. 실시간 이벤트 경로: App SDK → DARO API → Confluent Kafka → S3 → S3Queue Engine → ClickHouse. 앱에서 발생한 광고 노출/클릭이 Confluent를 통해 S3로 쌓이고, ClickHouse가 S3를 직접 폴링해서 자동 적재합니다. 정산 배치 경로: DARO Report Fetcher → S3 → Airflow → REPLACE PARTITION. 외부 SSP API에서 확정 리포트를 가져와 S3에 쌓고, Airflow가 해당 날짜 파티션을 원자적으로 교체합니다. S3가 허브 역할을 합니다. 두 경로 모두 S3를 거쳐 ClickHouse로 들어옵니다.

09 / 17Freshness
신선도: S3Queue Engine
기존 방식은 Airflow DAG가 S3를 폴링해서 ClickHouse에 INSERT하는 구조였습니다. 운영 복잡도가 높고 지연도 있었습니다. S3Queue Engine으로 바꾸면서 이게 사라졌습니다. ClickHouse가 S3 버킷을 직접 watch하다가 새 파일이 생기는 순간 자동으로 적재합니다. Airflow DAG가 필요 없어집니다. 설정은 CREATE TABLE ... ENGINE = S3Queue(...) DDL 하나로 끝입니다. 별도 오케스트레이션 없음, 운영 포인트 없음. 이게 TCO 관점에서 굉장히 매력적이었습니다.
9 / 17
10 / 17Accuracy
정확도: REPLACE PARTITION
확정 데이터를 업데이트할 때 흔히 쓰는 방법이 DELETE + INSERT입니다. 그런데 이 방법은 중간 상태가 생깁니다. DELETE가 완료되기 전에 쿼리가 날아오면 데이터가 비어 보일 수 있습니다. ClickHouse의 REPLACE PARTITION은 다릅니다. ALTER TABLE t REPLACE PARTITION p FROM t_tmp — 파티션 전체를 원자적으로 교체합니다. 교체 전후만 있고 중간 상태가 없습니다. 쿼리 중단 없이 정확도를 확보할 수 있습니다. D+7 확정 데이터가 도착하면 해당 날짜 파티션만 통째로 swap합니다. 깔끔합니다.

11 / 17★ Key Slide
하나의 테이블로 신선도와 정확도 동시에
이게 오늘 발표의 핵심입니다. agg_ssp_impression이라는 AggregatingMergeTree 테이블 하나로 두 가지를 동시에 만족시킵니다. 실시간 경로: stg_ssp__impression(S3Queue)에서 이벤트가 들어오면 Materialized View가 자동으로 agg_ssp_impression에 -State 집계를 누적합니다. sumState, uniqState 형태로요. 배치 경로: finalized_s3_source에서 확정 데이터가 오면 REPLACE PARTITION으로 해당 파티션을 정확한 값으로 교체합니다. 쿼리할 때는 sumMerge, uniqMerge로 -State를 최종화합니다. 같은 테이블, 같은 쿼리로 최신 실시간 집계와 확정 집계를 모두 읽을 수 있습니다.

13 / 17Warehouse
ClickHouse Cloud Warehouse
ClickHouse Cloud의 Warehouse 기능은 컴퓨트 노드들이 동일한 S3 스토리지를 공유할 수 있게 해줍니다. 이를 활용한 두 가지 사례를 소개드립니다. Use Case 01 — QA Staging 환경: Prod S3 데이터를 Staging ClickHouse가 그대로 참조합니다. 데이터 복사 없이 QA가 가능합니다. 스토리지 비용 이중 지불이 없습니다. Use Case 02 — Lightweight Data Lake: ClickHouse가 Query Engine 역할을 하고 S3가 스토리지입니다. Parquet, CSV 파일을 별도 ETL 없이 직접 쿼리합니다. 별도 Spark 클러스터나 Athena 없이 ClickHouse 하나로 해결됩니다.

14 / 17
15 / 17Takeaway 01
준실시간 집계 + 백필 집계를 하나의 테이블에
첫 번째 테이크어웨이입니다. AggregatingMergeTree 하나로 준실시간 스트림 집계와 D+1 백필 집계를 모두 담을 수 있습니다. 복잡한 파이프라인이 필요 없습니다. DDL과 DML만으로 ClickHouse 내에서 설정이 완결됩니다. Materialized View가 실시간으로 -State 집계를 누적하고, REPLACE PARTITION이 확정 데이터로 해당 파티션을 원자적으로 교체합니다. 쿼리 시에는 sumMerge / uniqMerge로 최종화합니다. 외부 오케스트레이션 도구를 최소화하면서, ClickHouse의 기능만으로 두 가지 요구사항을 동시에 만족시킬 수 있다는 게 핵심입니다.
15 / 17
16 / 17Takeaway 02
REPLACE PARTITION으로 재처리 파이프라인이 단순해집니다
두 번째 테이크어웨이입니다. REPLACE PARTITION을 활용하면 재처리 워크플로우가 4단계로 정리됩니다. CREATE TABLE tmp AS src로 스키마를 복사하고, INSERT INTO tmp로 새 데이터를 적재한 뒤, REPLACE PARTITION으로 원자적으로 교체하고, 마지막으로 DROP TABLE tmp로 정리합니다. Airflow DAG는 create_tmp >> load_tmp >> replace 세 태스크로 끝납니다. 멱등성(Idempotent)이 보장됩니다. 재실행해도 tmp 테이블을 매번 새로 만들고 지우기 때문에 중복 데이터 걱정이 없습니다. DELETE + UPSERT 방식 대비 중간에 쿼리해도 항상 일관된 결과를 보장합니다.

17 / 17Q&A
감사합니다 — Q&A
감사합니다. 질문이 있으시면 편하게 말씀해 주세요. 예상 Q1 — AggMT에서 -State / -Merge 함수를 꼭 써야 하나요?
네, 반드시 써야 합니다. AggregatingMergeTree는 raw 값이 아닌 직렬화된 집계 상태를 저장합니다. sumState로 넣고 sumMerge로 읽는 쌍이 맞아야 올바른 값이 나옵니다. 예상 Q2 — REPLACE PARTITION 도중 쿼리가 오면?
ClickHouse는 파티션 레벨 atomic swap이라 쿼리 결과가 old 또는 new 파티션을 완전히 읽습니다. 중간 상태가 없습니다. 예상 Q3 — S3Queue Engine은 exactly-once인가요?
At-least-once입니다. S3Queue 자체는 중복 가능성이 있습니다. AggregatingMergeTree의 집계 특성으로 멱등성을 확보하는 구조입니다.
