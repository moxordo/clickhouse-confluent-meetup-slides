02 / 17Company
사업 소개

Delightroom이라는 회사는 Alarmy라는 알람앱으로 시작했습니다.

알라미는 꽤나 초기부터 광고를 통한 앱 수익화를 시작했는데요, 그러다보니 고객에게 전달하는 가치의 사이즈에 비례하게 가치를 잘 Capture 할 수 있는 노하우나 광고 생태계에서의 기반을 잘 만들 수 있었던 것 같습니다.

알라미 처럼 국내외의 파트너들에게도 알라미의 광고 수익화 노하우와 광고 디멘드를 공유하고자 DARO라는 플랫폼을 런칭하고 운영해오고 있습니다. 감사하게도 많은 고객사분들이 만족하시고 홍보해주셔서 MAU 기준으로는 5천만, 파트너사 수로는 200 곳이 넘는 정도까지 성장 할 수 있었습니다.

근래에는 나아가서 이미 고객에게 가치를 잘 전달하고 있는 제품을 더 고도화하고 가꾸는 사업으로 나아가는 중입니다.

DARO에서의 챌린지

저희 DARO에서는 연동한 광고 지면에 대해서 대시보드 리포트를 제공합니다.

고객사 담당자께서 데이터를 확인하실때에 기대하시는 사항들이 몇 가지 있을텐데요, 그 중 중요한 두 개만 꼽아보자면 — 하나는 얼마나 최신의 데이터까지 보이는가, 또 다른 하나는 얼마나 정확하고 불변한 데이터가 제공되는가 일 것 같습니다.

08 / 17Pipeline
데이터 파이프라인

솔루션 본론에 들어가기에 앞서서 개괄적인 DARO의 데이터 파이프라인을 미리 보여드리겠습니다.

아마 "별거 없네?" 라고 생각하실 것 같습니다. 물론 각 레이어 안에는 추상화 시켜버린 부분들이 있지만, 실제 다뤄야하는 데이터 규모 대비 아키텍쳐가 복잡하지는 않다고 느끼실 수 있을 것 같습니다.

몇 가지 특이한 점이 있다면, ETL의 T에 해당하는 Transform을 맡아줄 컴포넌트를 따로 두지 않았다는 점인데요, 이는 ClickHouse의 compute를 잘 활용하고 Lake 처럼 활용하는 방식을 차용했기에 가능했습니다.

8 / 17
09 / 17Freshness
신선도 — S3Queue Engine

저희는 앞서 보여드린 것과 같이 S3를 주된 SSOT로 사용하고 있습니다. 그렇기에 S3로부터 자유롭게 데이터를 가져올 수 있는 것이 중요했는데, ClickHouse의 S3 engine이 초기에는 이 역할을 잘 수행해주었습니다. 단순히 S3에 접근하기 위한 credential (role이나 access_key)을 마련해주고 간단한 DML이면 데이터를 옮겨 올수 있습니다.

다만 기존의 S3 엔진은 INSERT INTO를 필요한 시점에 파티션 단위로 실행해주어야 하기 때문에 한 시간 이내의 데이터를 제공하기는 어려웠습니다.

다행히도 S3Queue Engine을 활용하면 S3에 적재될때 발생하는 이벤트를 기반으로 file 단위의 streaming이 가능해졌습니다.

이미 저희는 Confluent Connector를 통해서 S3까지 준실시간으로 쌓고 있었기 때문에 큰 문제없이 적용이 가능한 상태였습니다.

10 / 17Accuracy
정확도 — REPLACE PARTITION

두 번째 문제는 정확도 인데요, 데이터 엔지니어분들이 실무에서 항상 염두하시는 두 가지가 있다면 아마 하나는 Idempotency, 그리고 다른 하나는 Atomic Transaction 일 것 같습니다.

이를 만족하기 위해서 Iceberg의 ReplacePartition의 개념이 ClickHouse에도 존재할 것이라고 예상했고, 역시나 제공이 되어서 쉽게 활용이 가능했습니다.

11 / 17★ Key Slide
하나의 테이블로 신선도와 정확도 동시에

이제 신선도와 정확도를 동시에 맞추게 된 방법을 간략하게 공유할텐데요, 보시는 것과 같이 DDL, DML 몇 개만 엮어서 스케쥴러로 실행하실 수 있다면 저희가 풀고자 했던 문제를 쉽게 푸실 수 있습니다.

하나씩 차근차근 설명해드리자면, 우선 실시간으로 지표를 집계하기 위한 AggregatingMergeTree 기반의 테이블을 구성하고, 어떤 지표를 어떤 함수로 집계할 것인지를 명시합니다.

그 다음 이전 슬라이드에서 S3Queue로 셋팅한 테이블에서 데이터 업데이트 받아오는게 가능하도록 MV 설정을 하게 되구요. 그러면 이 시점에는 실시간 업데이트가 차근차근 들어오게 됩니다.

이제 일단위로 확정된 데이터를 업데이트 하고 싶을텐데요, 이미 partition 단위를 event_date로 설정해두었기 때문에 해당 파티션을 atomic하게 교체만 해주면 문제가 해결됩니다.

13 / 17Warehouse
ClickHouse Cloud Warehouse

저희는 쏠쏠하게 활용하고 있는 클릭하우스의 기능이라 가져와봤는데요, ClickHouse Cloud Warehouse라는 기능입니다.

많은 DB나 데이터 플랫폼들이 de-facto로 차용하는 전략이 된 storage-compute 분리하는 방식을 클릭하우스도 차용하고 있는데요, 그렇기에 가능한 기능이 웨어하우스 기능입니다. 고객 입장에서는 write와 read가 모두 횡적으로 스케일링이 가능해지기 때문에 얻을 수 있는 이점들이 있습니다.

저희는 이 기능을 활용해서 Staging이나 QA 환경으로 활용하고 있습니다. 보통 Staging 환경을 마련할때 어느 정도의 데이터를 준비해야하는가로 딜레마에 빠지게 되는데요, 스토리지 비용을 추가로 안내고 read replica만 추가하면 되기에 크게 고민 없이 쓰게 되었습니다.

다른 하나는 데이터 레이크로의 활용 가능성이 엿보였다는 건데요,
